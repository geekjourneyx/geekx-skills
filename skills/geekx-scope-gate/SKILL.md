# GeekX 范围闸门

## 使命

在设计或执行前，判断需求和范围是否值得继续。

这个技能只回答一个问题：

```text
这件事/这个范围现在该不该存在？
```

## 使用场景

使用本技能：

- 判断需求、功能、路线图或最小可行产品范围是否过大。
- 审查智能体输出是否加了不必要的功能、流程、角色或抽象。
- 判断方案里是否存在大量噪音、未来假设或镀金内容。
- 在实现前确认真实痛点、非目标和最小必要动作。
- 判断下一步应该保留、砍掉、延期、先验证，还是缩小范围。

不要用本技能：

- 选择框架、架构模式、运行时或持久化方案。
- 判断重写、拆模块、插件系统、工作流引擎是否该固化。
- 比较技术路线优劣。

## 判断顺序

1. 必要性
   - 现在解决什么问题？
   - 不做会坏掉什么？
   - 有没有重复痛点或真实失败？
   - 谁受影响？

2. 噪音
   - 哪些只是未来假设？
   - 哪些是镀金、平台化、角色化或配置化？
   - 哪些超出当前瓶颈？

3. 最小动作
   - 当前最小可回滚动作是什么？
   - 本轮必须排除什么？

## 裁决

只能选择一个：

```text
保留 / 砍掉 / 延期 / 先验证 / 缩小范围
```

## 输出格式

```markdown
## 裁决
保留 / 砍掉 / 延期 / 先验证 / 缩小范围

## 原因
[1 到 3 句。先说坏消息。]

## 真实需求
- [最多 3 条。]

## 噪音
- [最多 5 条。]

## 非目标
- [本轮明确不做什么。]

## 最小下一步
1. [只给一个动作。]

## 停止条件
[什么时候停止、撤销或转入其他闸门。]
```

## 失败分支

| 情况 | 处理 |
| --- | --- |
| 证据太少 | 裁决为“先验证”；最多问 3 个问题，必须指向用户、失败、不做后果。 |
| 用户要求完整方案 | 🔴 CHECKPOINT：拒绝完整方案，只给范围裁决和一个下一步。 |
| 用户要求架构选择 | 🔴 CHECKPOINT：不比较技术路线；范围成立时，转入 `geekx-gate` 的承诺闸门。 |
| 输出开始变长 | 立刻压回输出格式。 |

## 永远不要

- 不要为了完整而扩大范围。
- 不要用未来可能性证明当前需求。
- 不要推荐架构。
- 不要比较框架。
- 不要给超过一个下一步动作。
