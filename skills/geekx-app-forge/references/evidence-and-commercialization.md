# 证据链与商业化

## 证据链

只调研**会改变产品决定**的问题。不要为了“深度调研”堆链接。

每个关键主张记录：

| 字段 | 要求 |
|---|---|
| Claim | 我们现在相信什么 |
| Evidence | 支持证据 |
| Source | 一手来源优先 |
| Counter-evidence | 相反证据或限制 |
| Confidence | 高 / 中 / 低 |
| Product impact | 会改变哪个决定 |
| Next validation | 仍需验证什么 |

对实时变化的信息必须重新查证。

## 技术可行性

高风险能力必须优先检查：
- 官方平台文档；
- SDK/API 能力边界；
- 权限、签名、审核限制；
- 真机与模拟器差异；
- 开源 POC 是否真的覆盖目标场景；
- 不是“理论能做”，而是目标设备/版本是否支持。

如果核心能力未经验证，先做 Spike，不写完整产品计划。

## 真实需求信号

按可信度排序：
1. 用户自己反复遇到的真实场景和历史行为；
2. 真实用户主动寻找替代方案、付费或抱怨；
3. 同类产品持续活跃、评论和付费信号；
4. GitHub issue、论坛、Reddit、社区中的重复问题；
5. 搜索趋势和内容热度；
6. 纯观点和“看起来是机会”只算弱信号。

## 商业化镜头

先 dogfood，再回答：

- **可复制痛点**：有多少人不是因为认识作者才需要它？
- **使用频率**：一次买断工具还是持续使用产品？
- **迁移成本**：为什么从 Notes/Excel/现有 App 换过来？
- **独特优势**：数据、工作流、平台能力、生态、分发、品牌中的哪一项？
- **付费触发**：用户为什么在某个时刻愿意付钱？
- **边际成本**：商业化是否要求服务器、客服、审核、合规？
- **不污染 P0**：为了未来收费加入的功能是否让自用体验变差？

输出商业可能性，不虚构 TAM，不强行设计订阅。
